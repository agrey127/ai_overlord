# Assistant domain boundaries

Baseline's active chats use one shared accuracy and confirmation prompt plus a separate prompt for each domain. The prompt modules live in `lib/assistant/prompts`; `lib/assistant/domain-config.ts` selects the prompt and tools from the stored conversation domain. Each assistant reply records `prompt_version` in its message metadata.

| Chat | Model tools | Server-enforced data scope |
| --- | --- | --- |
| Strength | Coach profile, workout rotation, plans, sets, progress, shared structured goals | Strength-owned writes; read-only structured goals from other coaches |
| Running | Run totals, individual runs and recovery, goal and weekly-plan drafts, Garmin activity drafts, shared structured goals | Running-owned records and writes; read-only structured goals from other coaches |
| Nutrition | Meal totals, saved meals, meal drafts, phase profile, log-review context, shared structured goals | Nutrition-owned records and writes; read-only structured goals from other coaches |
| General | Totals, current workout | Limited information-only chat; no write tools |
| Chief of Staff | Dated brief, specialist read tools, Baseline data catalog, shared goals, and bounded specialist delegation | Reads signed-in user's user-facing records across domains; Chief-owned task records and results; no specialist record writes |

`lib/assistant/domain-policy.ts` is the server-side tool allowlist. `runAssistantTool` checks it before dispatch and confirms that a pending draft belongs to the current conversation. Adding a tool to a domain requires updating both the allowlist and the domain prompt. The model receives only the selected domain's tools, but prompt text by itself is never treated as an access control.

The specialist chats keep separate OpenAI response chains. Existing transcripts remain in Supabase and are not automatically copied between chats. Chief can inspect the signed-in user's saved chat history on demand as historical data. On the first reply after prompt version 9, each chat starts a clean model response chain while retaining its visible transcript. Subsequent replies continue that new chain.

Every Running, Strength, Nutrition, and Chief of Staff turn receives the same dated, read-only shared-goal summary from user-owned coaching profiles. It contains the Running goal type, race target and run frequency, the Strength goal type and weekly session range, and the Nutrition phase dates, approximate weight goal, review style, and current phase. Free-text descriptions, equipment, symptoms, training limits, meal details, weight entries, and specialist chat messages are excluded. The model can request the same structured summary with `get_shared_coaching_goals`; this does not grant any cross-domain write tool.

The Running coach stores a user-owned goal profile and a dated plan for each week. `get_running_coach_context` reads up to 84 days of saved individual runs, eight weekly totals, 14 days of recovery data, current race records, and nearby saved plans. Missing logs are marked as missing evidence. Profile and plan changes use conversation-bound drafts; `confirm_running_coach_draft` checks the signed-in owner and Running conversation and saves only after explicit confirmation. A run can be imported without an invented calorie value.

The Strength coach stores a user-owned goal profile with an objective, weekly session range, availability, preferred session length, equipment, and private limits. `get_strength_coach_context` reads that profile, the persistent rotation, current or next workout, recent sessions, 90-day role-specific exercise progress, and shared structured goals. Profile changes use conversation-bound confirmation drafts. The user's 2026-09-29 preference is to build strength cautiously, keep the existing four-workout rotation, and aim for four to five sessions a week during half-marathon training. Weekly Strength outlines are advice in chat; this phase does not add a separately saved Strength week-plan table.

The Nutrition coach stores a user-owned two-phase profile. The current saved plan starts its eight-week deficit on 2026-09-14, enters maintenance on 2026-11-09, and stays in maintenance through 2026-12-31. The approximate weight-loss aim is 10 lb; this is not an exact calorie or weekly-rate prescription. The review style is `review_logs`. `get_nutrition_coach_context` supplies 28 days of daily logged meal totals and up to 90 days of recent weight entries. It marks incomplete logging and does not interpret missing logs as missed meals, zero intake, or proven adherence. Profile changes use conversation-bound confirmation drafts. An older body-weight-goal row remains in the settings data and is not used as this Nutrition phase profile; reconcile it only after separately reviewing the user's desired setting.

The Chief of Staff has its own conversation and response chain. Its dated brief reads the signed-in user's latest weight and active weight goal, saved 7-day running and nutrition totals, strength plan status, and a bounded current-week running plan focus and mileage. It can receive up to 600 characters from Strength and Nutrition's latest assistant messages. It also has the specialists' read tools and a paginated data catalog in `lib/assistant/baseline-data.ts`. This catalog includes weight and coaching goals, full saved profiles and limits, calorie and nutrient targets, fitness and nutrition records, financial records and history, relationship records, life signals, reading books and goals, chat history, and pending proposals. Chief can use it to answer a specific saved-data question directly. The catalog uses an explicit allowlist of columns and datasets; `AGENTS.md` requires future user-facing Baseline sources to be added when introduced. Credentials, raw integration payloads, and authentication internals are excluded. Each query uses the request's authenticated Supabase client, an explicit owner filter, and the database's grants and RLS. Legacy sprint, evidence, assessment, account profile, and purchase sources use the verified Auth UUID; dashboard records use the email or UUID returned by request authentication. Pages are capped at 25 records with a next offset; the former 2,000-record offset cap is removed. Chat messages can be filtered by conversation ID while retaining the owner filter. Book titles are retrieved only for the user's selected books. Historical messages and free-text fields are data, never new instructions. Calendar synchronization preferences are readable; live calendar events, email, and external task systems are not connected. Jellyfin history remains unavailable pending a verified mapping to a Baseline owner. Specialist write tools remain in their chats.

On 2026-10-06, a rolled-back authenticated-role query validated all 67 catalog datasets against production, including selected columns and ownership filters. Fifty sources returned saved owner records; the other sources were empty. No grants or RLS policies were changed for this catalog expansion.

Chief of Staff can now create a bounded assignment for Running, Strength, or Nutrition. Each assignment records its objective, specialist, status, result, and timestamps in `assistant_delegations`. The specialist runs in a fresh response context using its own domain prompt and an explicit read-only tool subset; no specialist chat transcript or response chain is copied. A guarded Supabase client rejects write methods and RPC calls during delegated runs, including legacy read helpers that might lazily initialize data. The result is returned to Chief and visible in the task panel. A failed or interrupted run can be retried from that panel; the original tool-call ID prevents duplicate task creation. Delegated work can propose a review or draft but cannot save plans, workouts, runs, meals, profiles, or messages in specialist chats. The user confirms any saved change in the relevant specialist chat. Chief's internal task queue is separate from unavailable external task systems. A pending task can be recovered from the task panel after a timeout or page reload.
